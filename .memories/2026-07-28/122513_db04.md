## Closed the Vulkan zero-constant reproducibility defect locally

The RC5 package candidate was blocked because identical Windows toolchains emitted different `diag_f16` and `tri_f16` SPIR-V constants from pinned `D_TYPE(0)` shader expressions.

- **Root cause:** The untyped integer zero was lowered through an unstable 32-bit source constant before `OpFConvert` to half; RC4 happened to sample the zero variant twice.
- **Correction:** Strictly patch exactly one expression per pinned shader to `D_TYPE(0.0f)` and advance the content-derived identity to `vulkan-repro-v4`.
- **Permanent gate:** Both Bash and PowerShell Vulkan packaging parse generated `diag_f16.spv` and `tri_f16.spv` after compilation and before staging, requiring exactly one constant-derived half-float store sourced from zero.
- **Evidence:** Synthetic negative cases reject infinity, arbitrary nonzero, missing, duplicate, and malformed modules. The verifier accepts the actual first-run zero modules and rejects the actual second-run modules at `0x7f800000`.
- **Documentation:** RC4's Windows reproducibility claim is withdrawn, the incident is recorded, and RC5/promotion docs require the semantic bytecode gate plus two fresh byte-identical four-platform runs.
- **Review:** Grok returned `NO FINDINGS` and `READY FOR TWO FRESH FOUR-PLATFORM RUNS`.
- **Impact:** The old text-only/two-sample proof can no longer silently bless this failure class; RC5 artifact generation can proceed only after a fresh approved push.
